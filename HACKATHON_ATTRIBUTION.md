## Provenance statement

Every line of code, script, schema, document and demo asset in this repository was
created **inside the hackathon window**, starting on **October 26, 2026**. The repository
was initialised empty on that date and built up in phase-by-phase commits so the
history itself is the audit trail:

1. Root configuration, design system, demo IaC baseline and lab manifest
2. `packages/catalog` — Zod schemas, View Recipes, forced tool-calling schema
3. `packages/mcp-erp`, `packages/mcp-msgraph`, `packages/mcp-azure-iac` — MCP servers
4. `apps/orchestrator` — 4-Tier Meta Model Router
5. `apps/web` — ContextPane Operational Workbench
6. `scripts/` — PowerShell 7 lab seeding, teardown, router config, smoke test; `modal-sandbox/`
7. Verification run (typecheck + smoke test)

## Meta models used

This is the configuration the demo runs with: a `META_API_KEY` for the Meta Model API, a
Modal deployment of the open-weight Muse Glimmer 30B, and the Modal pre-flight sandbox.
Every id below appears in the router's own logs (`data/router-debug.jsonl` with
`CTX_ROUTER_DEBUG=1`) or in the tracked hover seed `data/hover-cache.seed.json`.

| Tier | Purpose | Model id (as sent) | Provider |
|---|---|---|---|
| 0 | Persistent View Recipe hydration | _none, 0 tokens_ | in-process MCP binding |
| 1A | Inline hover diagnostics (`AADSTS…` translation) | `muse-glimmer-30b` (open weights, `Muse-Glimmer-30B-GGUF` Q4_K_M on llama.cpp `llama-server`), then `muse-spark-1.3` | Modal L40S (scale to zero) → Meta Model API |
| 1B / 2 | Ticket ↔ Graph ↔ IaC correlation, layout hydration, N+k catalog gatekeeper, vision | `muse-spark-1.3` | Meta Model API |
| 3 | Remediation planning and PowerShell / Terraform / Graph synthesis, Sub-Agent coder, UI synthesizer, goal clarifier | `muse-wonder-1.0` | Meta Model API, verified in the Modal sandbox |
| Voice | Hands-free layout steering | `muse-voice-transcribe-1.0` (`POST /v1/asr/transcribe`), then `muse-spark-1.3` for the intent | Meta Model API |

**Stand-ins (disclosed).** The hackathon brief names two ids the Meta Model API does not
serve (checked against `GET /v1/models` on 2026-10-26): `muse-glimmer-30b` exists only as
open weights, and `muse-code` is not exposed. At startup
`apps/orchestrator/src/router/meta-models.ts` swaps any unserved Meta id for its stand-in
(`muse-glimmer-30b` → `muse-spark-1.3` on the Meta API, `muse-code` → `muse-wonder-1.0`), and
`GET /api/config` reports the swap under `metaModelResolution`. So Tier 3B code synthesis is
`muse-wonder-1.0`, not `muse-code`, and Glimmer is only ever the Modal open-weight deployment.

**Optional, not configured for the demo.** The router also knows Fireworks
(`accounts/fireworks/models/muse-glimmer-30b`) and Baseten (`meta-models/muse-spark-open-1026`)
as drop-in providers ahead of Meta. Neither has a key in the demo configuration, so neither
is in any chain and neither produced any answer shown in the video.

**Best Build on Meta Open Weight Models:** Muse Glimmer 30B runs from Meta's open weights on
our own Modal deployment (`modal-sandbox/glimmer_open_weights.py`), with
grammar-constrained JSON output (`response_format` with a JSON schema) for the hover
diagnostic. Every hover pill of the seeded scenarios was generated by it once and persisted
with its real latency and token counts (`data/hover-cache.seed.json`); a refresh re-runs it
live, and with `CTX_OPEN_WEIGHT_TIERS=hover,selection-prefetch` the selection prefetch runs on
it too. Telemetry and the hover popover name the provider that actually answered
(`modal-open-weights`, `meta` or `deterministic`).

**Best Agentic Use-Case:** Tier 3 is a Human-in-the-Loop agent loop. The model
synthesises an exact `Set-MgUserLicense` / `Update-MgIdentityConditionalAccessPolicy`
script and a Terraform NSG patch, the orchestrator verifies both in a pre-flight sandbox
(PowerShell AST parse + `terraform fmt`/`validate`, or a Modal sandbox), stages the patch
on a real git branch, and only then presents an approval drawer. Nothing executes
against a tenant without an explicit human click.
